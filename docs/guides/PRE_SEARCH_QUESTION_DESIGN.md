# 대화형 탐색 프로필 및 사전 질문 설계

- 작성일: 2026-08-21
- 상태: MVP 구현 계약
- 범위: 적금·예금·파킹통장·CMA 탐색 전 사용자 프로필 수집과 공통 우대조건 활용 의향 확인

> **후속 구현 기준:** Top 3 진입 후보군, 사용자 변수 단위 질문, 모호한 답변의 `확인 전` 처리, 정보성 혜택 제외와 완료 조건은 [`TOP3_CONDITION_QUESTION_IMPLEMENTATION_DESIGN.md`](TOP3_CONDITION_QUESTION_IMPLEMENTATION_DESIGN.md)를 따른다. 이 문서의 고정 질문 순서·공통 우대 의향 필수 질문·unknown 재질문 정책과 충돌하면 후속 문서가 우선한다.

> 후속 확장 설계와 1차 구현: 질문 도중의 자유발화, 질문 재노출을 LLM이 선택하는 방식, 검증 완료 Decision Ledger, 단일 LLM 호출, 전역 상품 feature policy와 정정·취소 계약은 [`FLEXIBLE_CONVERSATION_CONTEXT_AND_LEDGER_DESIGN.md`](FLEXIBLE_CONVERSATION_CONTEXT_AND_LEDGER_DESIGN.md)에 정리되어 있다. 이 문서의 기존 deterministic MVP 설명과 구분한다.

## 1. 목적

사전 질문의 목적은 사용자를 긴 고정 설문에 통과시키는 것이 아니다. Backend가 검색과 비교에 필요한 질문을 deterministic하게 제시하고, LLM은 자연어 답변을 재사용 가능한 사용자 탐색 프로필 patch로 구조화한다.

사전 질문은 두 종류로 나눈다.

1. 기간·금액처럼 상품 검색과 이자 계산에 직접 필요한 기본 질문
2. 첫 거래·급여이체처럼 여러 금융회사에서 반복되는 우대 유형을 활용할 의향이 있는지 묻는 일반 질문

일반 우대 의향은 특정 상품의 우대조건 충족을 확정하지 않는다. 먼저 해당 우대 유형을 고려할지 결정하고, 후보가 일부 은행과 상품으로 좁혀진 뒤 실제 조건을 넣은 질문으로 최종 확인한다.

## 2. LLM과 deterministic backend의 경계

```text
사용자 자연어
→ deterministic backend가 현재 상태에서 다음 고정 질문을 선택
→ LLM이 현재 답변의 의미, 모호성, 수정 의도를 차이 기반 patch로 해석
→ backend가 구조화된 사용자 탐색 프로필에 patch를 검증·병합
→ 가입 가능성, 세전 금리, 세전 이자액과 순위를 계산
```

LLM이 담당한다.

- 사용자가 이미 말한 정보를 찾아 불필요한 질문을 건너뛴다.
- 여러 답을 한 번에 이해하고 현재 프로필에 반영한다.
- `한 3년?`, `최대 1년`, `혜택이 크면 가능` 같은 표현의 의미를 해석한다.
- 모호한 선호와 타협 가능성을 자연어 맥락 속에서 유지한다.

Backend가 담당한다.

- 구조화 결과의 타입, 단위, 허용 범위와 충돌을 검증한다.
- 고정된 질문 풀, 순서, 적용 조건과 문구로 다음 질문을 결정한다.
- 명시적인 절대조건과 물리적인 가입 불가능 조건만 deterministic filter로 적용한다.
- 기간, 납입계획과 상품 정책으로 현금흐름을 계산한다.
- 금리와 예상 이자액을 **세전 기준**으로 계산하고 비교한다.

한국어 표현 목록이나 정규식 규칙을 확장해 의미를 결정하는 방식은 기본 설계로 사용하지 않는다. 사용자가 명시하지 않은 불가능·거절을 추론해 후보를 제거해서도 안 된다.

## 3. 질문 운영 원칙

- 아래 목록은 질문 풀이지 고정 순서의 설문지가 아니다.
- 사용자가 최초 발화에서 답한 항목은 다시 묻지 않는다.
- 검색에 필요한 최소 정보가 모이면 1차 후보를 만든다.
- 공통 우대 의향은 후보에 표시된 우대 유형과 관계없이 한 번은 반드시 묻는다.
- 동일한 프로필·의도·카탈로그 상태에서는 항상 동일한 다음 질문과 문구가 나온다.
- 일반 의향의 답변 상태가 `ACKNOWLEDGED_UNKNOWN`이면 우대 경로를 거짓이나 불가능으로 바꾸지 않는다.
- 일반 의향이 `WILLING`이어도 해당 상품의 우대금리를 확정 적용하지 않는다.
- 명시적인 거절만 해당 우대 경로를 사용하지 않는 근거로 삼는다. 상품 자체는 가입 가능한 경우 후보로 유지할 수 있다.

## 4. 기본 사전 질문 풀

### 4.1 상품 사용 목적과 돈을 넣는 방식

> 돈을 정기적으로 모으고 싶으신가요, 목돈을 일정 기간 맡기고 싶으신가요, 아니면 필요할 때 넣고 뺄 수 있는 계좌를 찾으시나요?

주요 구조화 값:

- `INSTALLMENT_SAVINGS`
- `TIME_DEPOSIT`
- `PARKING_ACCOUNT`과 `CMA`

아직 묻지 않았거나 사용자가 모르는 상태는 이 값에 섞지 않고 별도의 답변 진행 상태로 표현한다.

필요할 때 넣고 빼는 계좌를 원하지만 파킹통장과 CMA 중 하나를 명시하지 않았다면 두 상품군을 모두 1차 후보로 유지한다.

### 4.2 금액·납입 주기·기간

목돈을 맡기는 경우:

> 얼마 정도의 목돈을, 얼마나 맡기고 싶으세요? 대략적인 기간인지 반드시 지켜야 하는 기간인지도 함께 알려주세요.

정기적으로 모으는 경우:

> 얼마씩, 어느 주기로, 얼마나 모으고 싶으세요? 부담 가능한 최대 금액이나 반드시 지켜야 하는 기간이 있다면 함께 알려주세요.

파킹통장 또는 CMA를 찾는 경우:

> 평소 어느 정도 잔액을 보관할 예정인가요? 수익을 비교할 대략적인 기간도 함께 알려주세요.

수시입출금 상품의 기간은 가입기간이 아니라 비교를 위한 수익 계산 기간이다.

목표 금액과 최대 부담 가능액은 구분한다. 예를 들어 `월 30만 원을 생각하지만 최대 40만 원까지 가능`은 하나의 금액으로 합치지 않는다.

금액·납입 주기와 기간은 한 질문으로 받는다. LLM은 목표 금액, 최대 부담 가능액, 주기, 목표 기간, 범위, 유연성, 명시적인 상한·하한을 각각 구조화한다. 대략적인 기간은 선호로 사용하고 `최대`, `절대 넘지 않음`처럼 명시된 제한만 hard filter로 사용한다.

### 4.3 적금 검색의 전역 가입 자격 질문

정기적금 검색에서는 현재 후보 상품이나 사용자의 나이를 이유로 생략하지 않고 다음 질문을 각각 한 번씩 묻는다. 답변은 상품별 fact로 복제하지 않고 관련 상품 전체가 공유하는 전역 fact로 저장한다.

> 청년미래적금이 이미 있거나 청년도약계좌에 중복가입되어 있나요?

- 공통 fact: `YOUTH_FUTURE_OR_LEAP_ACCOUNT_HELD`
- 모든 청년미래적금의 중복가입 제한에 공통 적용한다.

> 현역병, 상근예비역, 의무경찰, 대체복무요원, 사회복무요원 중 하나에 해당하시나요? 모르거나 확인할 수 없으면 가입 불가로 처리됩니다.

- 공통 fact: `SOLDIER_TOMORROW_SAVINGS_ELIGIBLE`
- 모든 장병내일준비적금의 가입대상 판정에 공통 적용한다.
- 긍정만 `true`다. 부정, 모름, 확인 불가는 모두 `false`이며 장병내일준비적금 가입 자체를 `UNSATISFIABLE`로 판정한다.

### 4.4 예금자보호 및 CMA 포함 범위

파킹통장과 CMA가 후보에 함께 남아 있을 때만 묻는다.

> 예금자보호가 되는 입출금 계좌만 볼까요, 아니면 예금자보호 대상이 아니거나 수익이 달라질 수 있는 CMA도 함께 비교할까요?

권장 의미:

- `PARKING_ONLY`: 파킹통장만 유지
- `INCLUDE_CMA`: 파킹통장과 CMA를 모두 유지
- `CMA_ONLY`: CMA만 유지

실적배당 CMA를 확정금리 상품으로 바꾸지 않으며, 예금자보호 여부와 수익 구조는 발행 데이터에 있는 값만 표시한다.

### 4.5 자금을 유지할 수 있는 정도

적금이나 예금처럼 만기형 상품이 후보에 있을 때만 묻는다.

> 정한 기간 동안 돈을 그대로 유지할 수 있나요, 아니면 중간에 꺼내야 할 가능성이 있나요?

희망 가입기간과 자금 유동성은 별도 의미다. 사용자가 장기 상품을 선호하더라도 중도 인출 가능성이 있으면 중도해지·부분인출 정책을 추천에 반영한다.

### 4.6 금융기관 범위

> 은행 상품만 볼까요, 아니면 저축은행이나 증권사 상품도 함께 비교해도 괜찮으신가요?

권장 의미:

- `FIRST_SECTOR_ONLY`: 1금융권만 포함하는 hard constraint
- `PREFER_FIRST_SECTOR`: 1금융권을 우선하지만 다른 금융기관도 허용하는 preference
- `ANY`: 금융기관 종류와 무관하게 비교

아직 결정하지 못한 경우는 `ACKNOWLEDGED_UNKNOWN` 답변 상태로 저장한다.

금융기관 분류는 LLM이 상호명으로 추론하지 않는다. 카탈로그의 명시적인 기관 유형 메타데이터를 사용한다.

```text
COMMERCIAL_BANK
SPECIALIZED_BANK
REGIONAL_BANK
INTERNET_BANK
SAVINGS_BANK
CREDIT_UNION
OTHER
```

### 4.7 추천 기준 기본값

추천 기준은 사전 질문으로 묻지 않는다. 사용자가 별도로 기준을 말하지 않으면 `MAX_REALIZABLE_RATE`, 즉 확인된 조건으로 실제 적용 가능한 세전 금리가 높은 순으로 정렬한다.

사용자가 대화 중 `이자금순`, `세전이자`, `세후이자` 등 다른 기준을 명시하면 기존 ranking objective 변경 기능으로 반영한다. 확인되지 않은 우대금리, Data Gap 또는 실적배당 수익을 확정금리로 만들어 정렬하지 않는다.

## 5. 일반 우대조건 사전 질문 풀

### 5.1 추가 우대조건 통합 의향

> 더 유리한 혜택을 받을 수 있다면 새 금융기관 거래, 급여계좌 변경, 카드 사용 같은 추가 조건을 활용할 의향이 있으신가요?

첫 거래, 급여·소득 이체, 카드 관련 의향은 한 번에 묻는다. 단순한 긍정·부정은 세 유형 전체에 적용하고, 사용자가 `새 은행은 괜찮지만 카드는 만들고 싶지 않다`처럼 구분해 답하면 LLM이 다음 하위 의향을 각각 추출한다.

- `first_transaction_willingness`
- `salary_transfer_willingness`
- `card_willingness`

언급하지 않은 행동은 추론하지 않는다. 공통 의향 질문에는 상품별 은행, 판정기간, 실적금액을 넣지 않는다. 후보가 좁혀진 뒤 실제 상품 조건에 맞춰 별도로 검증한다.

급여를 받지 않거나 카드가 없는 것처럼 일부 행동만 적용되지 않으면 통합 질문 전체를 `NOT_APPLICABLE`로 닫지 않고 해당 행동의 하위 값을 `NOT_APPLICABLE`로 저장한다.

자동이체 설정은 일반적인 납입 편의 기능이므로 사전 질문에서 제외한다. 반면 카카오뱅크 한달적금처럼 **사용자가 매일 직접 입금해야 하는 조건**은 실질적인 부담이므로 상품별 검증 단계에서 정확한 기간과 횟수를 제시해 묻는다.

### 5.2 초기 공통 질문에서 제외하는 우대 유형

다음 조건은 카탈로그에서 반복되더라도 초기 질문 부담에 비해 후보군을 나누는 힘이 상대적으로 작아 기본 우대 질문에서 제외한다.

- 마케팅 동의
- 앱 가입·정기 로그인
- 오픈뱅킹·MyData 연결
- 이벤트·쿠폰 참여

이 조건은 좁혀진 후보의 세전 금리나 순위를 실제로 바꿀 때 상품별 후속 질문으로 묻는다.

## 6. 일반 우대 의향의 구조

통합 일반 우대 질문은 특정 은행의 사실이나 우대 달성을 저장하는 모델이 아니다.

```json
{
  "benefit_type": "COMMON_BENEFIT",
  "willingness": null,
  "action_preferences": {
    "FIRST_TRANSACTION_BENEFIT": "WILLING",
    "SALARY_BENEFIT": "CONDITIONAL",
    "CARD_BENEFIT": "UNWILLING"
  },
  "source_text": "새 은행은 괜찮고 급여는 혜택에 따라 가능하지만 카드는 싫어요"
}
```

답변 진행 상태와 의향 값은 분리한다.

진행 상태:

- `NOT_ASKED`: 아직 질문하지 않음
- `ANSWERED`: 의미 있는 답변을 구조화함
- `ACKNOWLEDGED_UNKNOWN`: 사용자가 모른다고 답했고 질문을 종료함
- `NOT_APPLICABLE`: 급여를 받지 않거나 카드가 없는 등 질문이 적용되지 않음

의향 값:

- `WILLING`: 해당 우대 유형을 활용할 의향이 있음
- `UNWILLING`: 해당 행동을 하지 않겠다고 명시함
- `CONDITIONAL`: 혜택이나 부담에 따라 가능함

`condition`은 자유로운 자연어로 유지할 수 있다. 모든 조건을 사전에 enum으로 만들지 않는다.

통합 답변에서 전체 의향과 행동별 의향이 함께 있으면 행동별 값이 우선한다.

## 7. 2단계 질문 흐름

```text
사용자 최초 발화
→ LLM이 최초 발화의 기본 조건을 IntentPatch로 구조화
→ backend가 이미 답한 고정 질문을 완료 처리
→ 1단계 기본 질문 중 다음 미완료 질문을 고정 순서로 제시
→ 내부 1차 후보 및 잠재 우대 경로 계산
→ 2단계 공통 우대 의향을 반드시 한 번 제시
→ 일부 은행·상품으로 후보 축소
→ 세전 금리와 세전 예상 이자액 기준 잠정 후보 표시
→ ranking-aware planner가 잠정 Top 후보의 실제 가입·우대조건 중 중요한 미확인 사실을 선택
→ LLM이 카탈로그 근거를 벗어나지 않는 자연스러운 상품별 질문을 작성
→ 사용자의 자연어 답을 LLM이 구조화하고 Engine이 재평가·재정렬
→ 중요한 미확인 조건이 없어질 때까지 반복
```

공통 의향은 `이 우대 경로를 비교 대상으로 유지할 것인가`만 결정하며, 상품별 실제 판정과 같은 사용자 사실로 저장하지 않는다. 사전 질문이 끝나면 별도 사용자 동작 없이 상품별 실제 자격·우대 검증으로 이어진다.

상품별 검증에서 Engine의 내부 미판정 상태 enum은 호환성을 위해 `UNKNOWN`을 유지하지만 사용자에게는 모두 `확인 전`으로 표시한다. 가입자격처럼 상품 가입 가능 여부를 결정하는 질문은 반드시 확인해야 하며 `아직 확인 전` 답변으로 완료 처리하지 않는다. 사용자가 확인할 수 없다면 사실을 임의로 참·거짓 처리하지 않고 해당 상품을 추천 후보에서 제외할 수 있게 안내한다. 우대금리처럼 가입 자체를 막지 않는 조건은 확인 전이면 해당 우대를 적용하지 않은 보수적인 금리로 계산할 수 있다.

## 8. 최종 선정 범위

초기 구현에서 우선 지원할 질문은 다음과 같다.

1. 상품 사용 목적과 돈을 넣는 방식
2. 금액·납입 주기·기간
3. 청년미래적금·청년도약계좌 중복가입 여부 전역 질문
4. 장병내일준비적금 복무 대상 여부 전역 질문
5. 파킹통장과 CMA가 함께 남을 때 예금자보호 및 CMA 포함 범위
6. 만기형 상품이 남을 때 자금을 유지할 수 있는 정도
7. 금융기관 범위
8. 새 금융기관 거래·급여계좌 변경·카드 사용 통합 의향

공통 우대 활용 의향은 항상 묻고, 나머지는 최초 발화에서 이미 확보한 답과 현재 상품군에 적용되지 않는 조건을 건너뛴다. 추천 기준은 묻지 않고 금리순을 기본으로 한다. 사전 질문의 선택과 문구에는 LLM을 사용하지 않고, 그 이후 상품별 질문의 선택은 Engine, 자연어 표현과 답변 해석은 LLM이 담당한다.

## 9. 구현 시 지켜야 할 불변조건

- 기본 금리·우대금리와 예상 이자액은 세전 기준이다.
- 일반 우대 의향만으로 특정 상품의 우대금리를 확정하지 않는다.
- `NOT_ASKED`와 `ACKNOWLEDGED_UNKNOWN`을 합치지 않는다.
- `ACKNOWLEDGED_UNKNOWN`을 `UNWILLING` 또는 `false`로 바꾸지 않는다. 단, 장병내일준비적금 복무 대상은 가입 필수 자격이므로 모름·확인 불가를 `false`로 확정하고 가입 불가로 판정한다.
- `CONDITIONAL`을 임의의 금액 기준으로 자동 변환하지 않는다.
- 사용자가 명시한 절대조건이 아니면 후보를 성급하게 제거하지 않는다.
- 상품별 검증 질문은 카탈로그에 근거가 있는 실제 조건만 사용한다.
- 질문 문구를 위한 대표 기간과 실제 eligibility 판정 기간을 분리한다.
- 금융기관 유형은 카탈로그 메타데이터로 판정한다.
- 기본 정렬은 `MAX_REALIZABLE_RATE`다.
- 상품별 검증 전 결과는 확정 추천이 아니라 잠정 후보로 표시한다.
