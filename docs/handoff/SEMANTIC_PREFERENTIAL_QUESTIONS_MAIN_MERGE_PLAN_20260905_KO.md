## 1. 한 줄 요약

하려는 검색은 이것이다.

1. 지금처럼 사전 질문으로 후보를 줄이고 순위를 매긴다.
2. 상위권과, 아직 올라올 수 있는 후보만 고른다.
3. 컴퓨터가 아직 못 읽은 우대조건 글을 AI가 한 묶음으로 읽는다.
4. 같은 종류의 사용자 입력은 한 질문으로 묶는다.
5. 답을 받은 뒤 금리와 순위는 지금 계산기가 다시 계산한다.

이 순서 자체는 기능 브랜치에 들어 있다. 스위치 기본값은 꺼짐이다.

다만 테스트에서 본 “자녀 질문 한 번에 예상 금리가 오른다”는 장면은 **가짜 상품** 기준이다. 실제 카탈로그에서는 공통 질문이 잘 안 묶이고, 답을 해도 예상 금리가 잘 안 오른다. 공통 질문의 본업은 **해당 없는 우대를 빼는 것**으로 본다. 금리를 더하는 것은 가능할 때만 한다.

**main에 지금 바로, 켜진 채, 한 덩어리로 넣지 않는다.**  
스위치 꺼진 실험 코드로 넣더라도, 관련 없는 카탈로그 수정과 나누고, 아래 안전 장치를 먼저 정한 뒤에 넣는다.

## 2. 배경과 현재 상태

### 2.1 왜 이 기능이 나왔는가

정규화 카탈로그에는 이미 기계가 실행하는 우대 규칙이 많다. 동시에 원문만 있고 실행 규칙이 없거나, “원문 한 문장 전체 = 예/아니오”로만 막혀 있는 우대도 있다. 그런 글까지 상품마다 “해당하나요?”로 물으면 질문이 너무 쪼개진다.

그래서 상위 후보의 그런 글만 그때그때 읽고, 사람 기준으로 같은 입력이면 한 번만 묻자고 한 것이다. 전 상품을 미리 AI로 재발행하지는 않는다.

### 2.2 지금 어디에 있는가

## 3. 기능 브랜치가 실제로 하는 일

아래는 구현된 동작이다. 우리가 바꾸려는 부분과 유지할 부분을 나눌 때 기준으로 쓴다.

### 3.1 검색 한 턴의 순서

1. 기존 사전 질문(상품 종류, 기간·금액, 나이, 은행 범위, 추가 거래 의향, 최근 예적금 보유 기관 등)을 먼저 한다.
2. 사전 질문이 남아 있으면 우대 글은 읽지 않는다. 상태는 `DEFERRED`다.
3. 후보를 거르고, 지금 엔진으로 평가하고, 순위를 매긴다.
4. 읽을 대상은 “서로 닮은 상품”이 아니다.
   - 지금 상위(요청한 Top-K)
   - 아직 3위권에 들어올 수 있는 후보
   - 비교 가능한 상한이 없는 후보
5. 그중에서도 실행 규칙이 없는 우대 원문, 그리고 “원문 한 문장 = 예/아니오”로만 막힌 조건만 모은다. 이미 숫자로 잘 분해된 규칙은 읽기 전용 참고만 한다.
6. 한 번의 쓰기 요청에서 기본 최대 **8상품 / 48원문 / 50,000자**만 읽는다. 이건 후보 삭제 한도가 아니라 **이번 턴 읽기 양**이다. 나머지는 삭제하지 않고 `PENDING`으로 남긴다.
7. AI는 금리·순위·사용자 사실을 만들지 않는다. 고정된 표현(그리고/또는, 자녀 수, 자녀 있음, 혼인일, 임신, 모름)만 반환한다.
8. 프로그램이 원문 해시, 절 ID, 인용문, 숫자의 글자 근거를 검사한다. 묶음 하나가 실패하면 그 묶음은 쓰지 않는다.
9. 통과한 해석만 이번 검색 세션에 잠깐 붙인다. 원본 카탈로그는 바꾸지 않는다.
10. 같은 사용자 입력 칸은 기존 질문 플래너가 한 질문으로 묶는다.
11. 답을 받으면 지금 계산기가 금리와 순위를 다시 계산한다.
12. 목록 새로고침(GET)은 글을 다시 읽거나 캐시를 쓰지 않는다. 다음 묶음은 명시적인 “계속 분석” 또는 다음 답변 때 읽는다.

### 3.2 AI가 아는 칸 (현재 코드)

지금 코드가 공통 질문으로 인정하는 칸은 셋이다.

- 자녀(수, 출생연도/출생일)
- 혼인일
- 가입자 본인 임신

그 밖의 원문은 `UNKNOWN`이거나 해석 불가다. 급여이체, 카드, 마케팅 동의, 첫거래 등은 이 기능의 새 칸이 아니라, 원래 엔진·사전 질문 쪽에 남아 있다. 다만 아래 후속 작업에서 **이미 있는 질문에 연결**하는 것은 한다. 새 칸을 처음부터 많이 만들지는 않는다.

### 3.3 답을 받은 뒤의 세 갈래

각 우대는 이렇게 나뉜다.

- **해당 없음:** 우대에서 뺀다. 상한도 내린다. 공통 질문의 본업이다.
- **아직 모름:** 빼지도 더하지도 않는다. 상한만 남긴다. “해당될 수 있으나 정보가 더 필요함 / 은행 확인이 필요함”이 여기 해당한다.
- **해당함:** 사용자 말만으로 인정되는 우대일 때만 예상 금리에 더한다. 실제 발행 카탈로그에서는 이 갈래가 드물다.

출생연도만 있고 생일이 경계에 걸리면 1월 1일로 추측하지 않는다. “모름”은 자녀 없음으로 바꾸지 않는다. AI가 글을 읽은 추천은 `PROVISIONAL`(잠정)로 남긴다.

## 4. 검토에서 확인한 사실 (머지 판단의 근거)

### 4.1 잘 된 점

- 기존 사전 질문과 계산기를 교체하지 않는다.
- 스위치 기본값이 꺼져 있다.
- GET이 분석을 다시 돌리지 않는다.
- 컴파일 실패 시 잘못된 해석을 적용하지 않고, typed 질문은 남긴다.
- 스크립트 LLM + 실제 엔진·플래너·HTTP 회귀 47개가 통과한다.
- 원격 전체 pytest가 통과한다.
- 사용자 답을 기관 증빙으로 올리지 않는다.
- 읽을 대상을 전 카탈로그가 아니라 현재 순위 후보로 한정한다.

### 4.2 main에 넣기 전에 알아야 할 간격

**공통 질문 매핑이 테스트 픽스처에 맞춰져 있다.**  
코드는 `CHILD_COUNT`, `MARRIAGE_DATE`, `PREGNANT_SELF`만 기존 typed 조건과 묶는다. 발행 카탈로그의 실행 이름은 `HOUSEHOLD_QUALIFYING_CHILD_COUNT`처럼 다르다. 그래서 데모의 “한 질문으로 typed+원문 동시 해결”은 실제 상품에서 거의 재현되지 않는다.

**실제 원문 916개 조사가 `official_only`다.**  
`self_report_eligible: true`인 compile 대상 절이 0개였다. 사용자 답을 받아도 예상(realizable) 금리에 잘 안 넣는다. 테스트에서 금리가 오른 이유는 가짜 상품에 “사용자 말로 인정”을 넣었기 때문이다.

**같은 원문의 티어 우대를 더할 수 있다.**  
예: 자녀사랑우대적금은 “1명이면 1%, 2명이면 2%, 3명이면 3%”가 규칙 세 개로 나뉘어 있고, 배타 관계가 비어 있다. 지금은 실행 규칙이 없어 광고 상한 한 덩어리로만 잡힌다. 해석을 실행 규칙으로 올리면 1+2+3이 될 수 있다. 이건 AI 문장 이해만의 문제가 아니라 **계산기 규칙**이다.

**빈 원문 하나면 그 상품 전체가 실패한다.**  
packet이 생기는 상품은 4,295개 중 384개, 절 916개. 그중 45개 상품은 빈 글 때문에 통째로 `SOURCE_PACKET_UNSUPPORTED`가 된다.

**숫자/인용 검사만으로 뜻이 맞다고 볼 수 없다.**  
“미성년 자녀 1명”을 나이 없이 `자녀 ≥ 1`로 읽어도, 원문에 `1`이 있으면 통과할 수 있다.

**한 턴이 동기 LLM이라 느릴 수 있다.**  
프로필 타임아웃 30초, 재시도 가능. 웹은 사전 질문이 끝난 직후 같은 요청에서 읽을 수 있다.

이 간격이 있어서, main 머지를 “검색이 데모처럼 동작한다”는 의미로 보지 않는다.

## 5. 우리가 합의한 작동 방식 (후속 구현의 고정 결정)

아래는 다시 논쟁하지 않고 구현에 반영한다.

### 5.1 공통 질문의 본업

해당 없는 우대를 빼는 것이 본업이다. 확실한 경우에만 더한다. 성공 기준을 “예상 금리가 올랐는가”만으로 두지 않는다.

### 5.2 같은 칸은 전처리가 아니다

카탈로그를 미리 돌려 “자녀 칸 상품끼리” 모아 두지 않는다. 임베딩으로 비슷한 상품을 고르지도 않는다.

순서:

1. 지금처럼 질문·필터·순위를 한다.
2. **지금 위에 있는 후보**의 못 읽은 글만 읽는다.
3. 그때 글이 어느 칸인지 고른다.
4. 같은 칸으로 들어간 것만 질문을 한 번으로 묶는다.

비슷한 상품끼리 모으면, 닮지 않았지만 같은 사람 사실(자녀)을 쓰는 상품이 갈라져 질문이 두 번이 된다.

### 5.3 칸은 짧게, 이미 있는 질문에 먼저 붙인다

칸을 백지로 많이 만들지 않는다. 이미 물어보는 것부터 파악한다.

| 이미 있는 질문 | 이 기능에서 할 일 |
|---|---|
| 적금/예금, 기간, 금액, 나이, 은행 범위 | 다시 묻지 않음 |
| 새 거래·급여계좌·카드 의향 (사전 질문) | 새 칸 만들지 않음. 원문이 마케팅/카드/급여 의향이면 여기로 연결 |
| 최근 6개월 예적금·청약 보유 기관 (첫거래 판단용) | 새 칸 만들지 않음. “새 계좌 내도 되냐”와 첫거래를 섞지 않음 |
| 카드 실적, 급여이체처럼 이미 숫자로 있는 조건 | 기존 질문 묶기 유지 |
| 자녀·혼인·임신처럼 글만 있고 공통 질문이 약한 것 | AI 칸으로 유지·보강 |

마케팅 동의는 “앞으로 동의할 의향”이면 여러 은행에 같이 쓸 수 있다. “경남은행에 이미 동의됨”은 신한으로 옮기지 않는다.  
첫거래는 원문이 정한 기간·상품 종류·기관 범위로 판단한다. 최근 6개월 예적금·청약 보유 기관만으로 모든 첫거래 우대를 제외하지 않는다.

### 5.4 한 번에 8개, 아래는 다음 묶음

8개는 후보 수가 아니라 이번 턴 읽기 양이다. 올라올 수 있는 후보는 이미 읽기 대상에 들어 있다. 나머지는 `PENDING`으로 두고, 답을 받거나 “계속 분석”을 누른 뒤 **다음 8개**를 읽는다.

검색 중에 아래 상품을 병렬로 미리 다 읽지 않는다. 답이 나오면 순위가 바뀌고, 시간도 길어진다.

### 5.5 메모는 엔진 상태, 설명은 원문

AI에게 상품마다 설명 문장을 새로 쓰게 하지 않는다. 그러면 질문이 상품별로 쪼개진다.

엔진이 이미 아는 상태만 메모로 붙인다.

- 해당 없습니다
- 해당될 수 있습니다. 자녀 수(또는 생년월일 등)를 더 알면 판단할 수 있습니다
- 조건은 맞을 수 있으나 은행 확인이 필요합니다
- 이 우대는 자동으로 판단하지 못했습니다

원문 한 줄을 그대로 옆에 보여주는 것은 된다. 상태 종류를 AI가 고르지는 않는다.  
은행 약관의 모든 문장을 미리 적을 필요는 없다. 칸에 들어가는 입력 종류가 늘 때만 메모 문장이 한 줄 늘어난다. 칸에 못 넣는 긴 꼬리는 모두 “자동 판단 못함”이다.

### 5.6 같은 원문의 티어는 더하지 않는다

같은 글에서 나온 1%/2%/3%는 합치지 않고, 맞는 것 하나만 쓴다. 이 규칙은 계산기가 담당한다. AI가 잘 읽기를 기다리지 않는다.

### 5.7 1금융권은 조사 범위이지, 검색 강제 필터가 아니다

칸을 정하려고 표본을 볼 때는 **1금융권부터** 본다. 상품이 4천 개 가까이여서다.

실제 검색에서는 사용자가 이미 “은행만”이라고 답하면 후보가 그때 은행만 남는다. 기능을 은행 전용으로 고정하지 않는다. 저축은행까지 보겠다는 사람에게 은행만 읽으면 비교가 기울어진다.

---

## 6. main에 넣는 원칙

1. **기본 꺼짐.** 스위치를 켜지 않으면 지금 main과 같아야 한다.
2. **계산기는 진실의 원천이다.** AI는 글을 칸에 넣는 일만 한다. 금리·순위·더하기/빼기는 코드다.
3. **데모 문장으로 머지 공지를 쓰지 않는다.** “자녀 답하면 2%→3%”는 가짜 상품 결과라고 명시한다.
4. **관련 없는 커밋과 나누어 넣는다.**
5. **잠정 표시를 유지한다.** AI가 읽은 추천은 확정이 아니다.
6. **전 카탈로그 LLM 전처리를 이 머지에 넣지 않는다.**
7. **벡터 임베딩을 이 머지에 넣지 않는다.**

---

## 7. 머지 단계

기능 브랜치를 지금 상태 그대로 main에 합치지 않는다. 아래 순서를 따른다.

### 단계 0 — 이 문서 (지금)

main에 계획 문서만 넣는다. 런타임 동작은 바꾸지 않는다.

산출물: 이 파일, `docs/README.md` 링크.

### 단계 1 — 기능 브랜치를 두 갈래로 나눈다

`codex/semantic-preferential-questions`에는 서로 다른 일이 섞여 있다.

**갈래 A. 추천 감사 수정 (이미 기능과 별개)**

- 카카오 예금 기간 도메인 발행
- 기간 하한/상한 처리
- 질문 frontier의 보수적 하한
- 대화 대상 grounding
- GET이 업무 상태를 진행시키지 않게 한 수정

이 갈래는 의미 분석 기능과 별도로 리뷰·머지한다. 이미 `docs/recommendation-audit-fixes.md`가 있다.

**갈래 B. 의미 분석 MVP**

- `src/eligibility/search/semantic.py`
- `src/eligibility/semantic_augmentation.py`
- `src/eligibility/schema/semantic.py`
- 질문 플래너·ApplicationService·REST·Web 연결
- `tests/test_semantic_preferential_questions.py`
- `docs/semantic-preferential-questions.md`

main에 넣을 PR은 B만 대상으로 한다. A가 먼저 들어가 있으면 B는 그 위에 재배치한다.

### 단계 2 — B를 main에 넣기 전에 반드시 고칠 것

스위치 꺼진 채라도, 켜면 금리를 **과대 합산**할 수 있는 구멍은 먼저 막는다.

1. **같은 조건의 단계별 보상만 최댓값으로 쓴다.**  
   원문 문자열이 같다는 이유만으로 독립 우대를 묶지 않는다.  
   자녀사랑우대적금형 티어가 대표 사례다. 테스트에 “같은 문장, 보상 1/2/3, 자녀 3명 → 합이 아니라 3%”를 넣는다.
2. **빈 원문 하나가 상품 전체를 실패시키지 않게 한다.**  
   빈 절만 건너뛰고, 나머지 절은 읽는다. 빈 절은 “판단 못함” 메모로 남긴다.
3. **기능 문서와 PR 본문에 실제 카탈로그 한계를 적는다.**  
   typed 공통 질문이 픽스처 전용인 점, 대부분 은행 확인이라 예상 금리가 잘 안 오르는 점, 실제 외부 모델 미검증.
4. **추천 상태가 잠정인 이유와, 상품 옆 메모의 네 종류를 명세에 고정한다.**  
   구현은 단계 3에서도 되지만, 계약은 단계 2에서 적는다.

이 네 가지가 없는 B는 main에 넣지 않는다.

### 단계 3 — 꺼진 스위치로만 main에 넣는 조건

단계 2가 끝난 뒤에만, 갈래 B를 main에 넣을 수 있다. 그때도 다음을 지킨다.

- 기본값 꺼짐. 웹 런타임은 환경변수가 켜져 있고 gateway가 있을 때만 컴파일러를 붙인다.
- 기존 테스트가 스위치를 켜지 않아도 통과한다.
- 신규 테스트는 스크립트 LLM을 쓰고, 실제 카탈로그 상품 최소 1개(애랑해적금 intake 등)를 유지한다.
- 운영/기본 `.env.example`에 스위치를 켜지 않는다. 꺼져 있음을 명시한다.
- PR 제목·본문에 “실험적, 기본 꺼짐, 실제 모델 미검증”을 적는다.

이 단계의 목적은 “코드가 main에 들어와 다른 작업과 크게 어긋나지 않게 하는 것”이다. 사용자에게 켜서 보여 주는 단계가 아니다.

### 단계 4 — 켠 채로 쓰기 전에 할 일 (main 머지 이후, 배포 전)

아래가 끝나기 전에는 기본 스위치를 켜지 않고, 데모도 “예상 금리가 오른다”로 홍보하지 않는다.

1. 1금융권 표본 조사 (8절)
2. 기존 사전 질문·질문 묶기와 칸 연결표 (8절)
3. 엔진 상태 메모를 상품 상세에 표시 (8절)
4. 실제 외부 모델로 1금융권 상위 후보 몇 건을 읽어, 칸 분류가 얼마나 맞는지 기록
5. 같은 원문 티어·은행 확인·해당 없음 빼기가 실제 상품에서 보이는지 확인

## 8. 이후 진행할 작업 (자세히)

작업은 검색 중에 4천 개를 읽는 것이 아니다. **칸을 정하고, 빼기/메모/티어를 엔진에 고정하는 일**이다.

### 작업 1. 지금 이미 물어보는 것 목록화

담당 질문의 출처는 코드에 이미 있다. 새로 발명하지 않고 표를 만든다.

사전 질문 (`src/eligibility/search/pre_search.py`의 순서):

1. 적금/예금/파킹 등 상품 종류
2. 납입과 기간
3. 가입 명의
4. 생년월일
5. 청년 정책형 적금 중복
6. 장병내일준비적금
7. 예금자보호·CMA 범위
8. 은행 / 저축은행 / 증권 범위
9. 새 거래·급여계좌·카드 등 추가 조건 의향
10. 최근 6개월 예적금·청약 보유 기관

그다음 상품 조건 질문은 `RankingAwareQuestionPlanner`가 묶는다. 이미 특별 취급하는 예:

- 카드 실적 한도
- 급여이체
- 첫거래/신규고객 (과거 보유 이력)
- 마케팅 동의 문구를 “가입 후 유지를 할 수 있나요?”로 바꿈

산출물: `docs/handoff/` 또는 이 문서 부록에 **질문 ID → 의미 → 이 기능이 다시 물으면 안 되는지** 표.

완료 기준: 표에 없는 칸을 만들기 전에, 있는 질문에 붙일 수 있는지 먼저 적는다.

### 작업 2. 1금융권 표본으로 못 읽은 우대 글 분류

범위:

- 기관 유형이 은행(`BANK`)인 상품
- 그중 지금 기능이 packet을 만드는 것(실행 규칙 없음 또는 원문 게이트)
- 전 카탈로그 4천 개가 아님
- 검색 런타임을 은행만으로 강제하지 않음

각 절을 다음 중 하나로만 분류한다.

- 기존 사전 질문 9번(추가 의향)에 연결 가능
- 기존 사전 질문 10번(보유 기관)에 연결 가능
- 기존 typed 카드/급여 질문에 연결 가능
- 자녀/혼인/임신 칸
- 연결할 곳 없음 → 이번엔 판단 못함으로 둘 것
- 같은 원문 티어(1명/2명/3명) → 계산기에서 최댓값

분류는 사람이 보고, 필요하면 스크립트로 키워드·`source_semantics`만 집계한다. 이 조사 단계에서 전 상품 임베딩을 만들지 않는다.

산출물:

- 1금융권 packet 상품 수, 절 수
- 위 분류 비율
- “새 칸이 꼭 필요한가?”에 대한 예/아니오. 기본 예상은 **아니오. 기존 질문을 우선 재사용하고 추가 질문은 자녀·혼인·본인 임신으로 제한**

완료 기준: 새 칸 제안이 나오더라도, 기존 질문으로 부족한 이유가 한 문장으로 적혀 있어야 한다.

### 작업 3. 기존 질문에 원문 해석 연결

AI가 “마케팅 동의 하실래요?”를 새로 만들지 않게 한다. 원문이 마케팅/첫거래로 분류되면:

- 이미 사전 질문에서 추가 의향을 거절한 경우 → 그 우대는 빼거나 비교 대상에서 이미 빠진 상태를 존중
- 보유 기관 답으로 원문 기간·상품 종류의 불충족이 입증되면 → 해당 없음
- 기간·상품 범위가 다르거나 목록에 없으면 첫거래를 충족으로 확정하지 않음 → 메모 “은행 확인 필요”

자녀 칸만 남기고 마케팅을 또 묻는 중복을 테스트로 막는다.

### 작업 4. 상품 옆 메모

`semantic_interpretations`에 상태 코드를 넣는다.

| 코드 | 화면 문장 |
|---|---|
| `RULED_OUT` | 이 우대는 현재 답 기준으로 해당 없습니다 |
| `NEEDS_INPUT` | 해당될 수 있습니다. (부족한 칸 이름)를 더 알면 판단할 수 있습니다 |
| `NEEDS_OFFICIAL` | 조건은 맞을 수 있으나 은행 확인이 필요합니다 |
| `UNRESOLVED` | 이 우대는 자동으로 판단하지 못했습니다 |

표시 위치: 목록의 “N개 미분석” 배너가 아니라 **상품 카드/상세**.  
질문은 지금 필요한 공통 칸 하나, 메모는 왜 아직 확정이 아닌지의 설명. 둘 다 있어도 된다.

문장은 코드가 고른다. AI는 원문 인용만 해도 된다.

테스트:

- 자녀 0명 → `RULED_OUT`, 상한 하락
- 출생연도만 있고 경계 → `NEEDS_INPUT`, 생일 질문
- 은행 확인 필요 → 답해도 예상 금리 불변, `NEEDS_OFFICIAL`
- 해석 실패 → `UNRESOLVED`, 상품은 후보에 남음

### 작업 5. 같은 원문 티어는 최댓값

계산 단계에서, 같은 조건의 단계별 보상(예: 자녀 1/2/3명)은 합치지 않고 최댓값만 쓴다. 한 문장에 함께 적힌 독립 우대는 합산한다. 관계가 불명확하면 배타 그룹을 만들지 않는다.

테스트 픽스처: 가짜 상품이 아니라 실제 `자녀사랑우대적금`형 구조(동일 문장, 보상 1/2/3, relations 빈 배열).

### 작업 6. 읽기 묶음과 다음 8개

지금 구현(8개씩, 계속 버튼, 답 후 순위 재계산)을 유지한다. 여기에만 보강한다.

- 다음 묶음은 **답이 반영된 새 순위** 기준이다. 예전에 찍어 둔 아래 상품을 그대로 읽지 않는다.
- 검색 시작 시 아래 상품 병렬 선읽기를 넣지 않는다.
- 한 턴이 너무 길면, 1묶음만 읽고 질문은 기존 엔진 것부터 내되, 분석 중임을 표시하는 방안을 나중에 검토한다. 1차 머지 조건은 아니다.

### 작업 7. 실제 모델 확인 (스위치 켜기 전)

스크립트 테스트만으로 켜지 않는다. 1금융권 검색 시나리오 소수:

- 사전 질문 후 상위 후보에 자녀 우대 글이 있는 경우
- 마케팅/첫거래 글이 있는 경우 (기존 질문에 붙는지)
- 티어 문장이 있는 경우 (합치지 않는지)

기록할 것: 칸 분류가 맞았는지, 질문 횟수, 예상 금리 변화(오름이 아니라 빼기가 맞았는지), 걸린 시간.  
품질이 나쁘면 칸을 늘리지 말고, 못 읽은 것을 `UNRESOLVED`로 더 많이 남긴다.

### 일부러 하지 않는 것

- 상품 벡터 임베딩으로 유사 상품 선정
- 전 카탈로그 LLM 전처리·재발행
- 원문 종류별 한국어 메모를 사전 작성
- AI에게 상품별 질문을 자유 생성하게 하기
- “모름”을 자녀 없음으로 바꾸기
- 사용자 답을 은행 서류 확인과 같게 취급하기
- 이 기능을 1금융권 전용으로 하드코딩하기
- 스위치 기본값을 켜기

## 9. 추천하는 실제 순서

지금 당장 코드부터 기능 브랜치를 main에 넣지 않는다.

1. 이 문서를 main에 넣는다. (단계 0)
2. 작업 1(기존 질문 표)과 작업 2(1금융권 표본 분류)를 한다. 런타임 변경이 거의 없다.
3. 작업 5(티어 최댓값)와 빈 원문 부분 실패를 기능 브랜치에 고친다. (단계 2)
4. 갈래 A/B를 나눈 PR을 검토한다.
5. 꺼진 스위치로 갈래 B만 main에 넣을지 결정한다. (단계 3)
6. 작업 3·4(연결·메모)를 main 위에서 이어 한다.
7. 작업 7(실제 모델) 후에만 켜는 것을 검토한다.

2번과 3번은 서로 막을 필요가 거의 없다. 조사와 티어 가드는 같이 진행해도 된다.

## 10. 성공을 무엇으로 볼지

### main에 꺼진 채 넣어도 되는 시점

- 스위치를 끄면 기존 검색과 같다
- 같은 원문 티어를 더하지 않는다
- 빈 절이 상품 전체를 버리지 않는다
- 문서가 실제 카탈로그 한계를 숨기지 않는다
- 관련 없는 카탈로그 발행과 PR이 분리되어 있다

### 스위치를 켜도 된다고 보는 시점

- 1금융권 표본에서, 못 읽은 글의 상당수가 **기존 질문 또는 자녀 칸**으로 분류된다
- 공통 질문 한 번에 여러 상위 상품의 해당 없는 우대가 빠진다
- 애매한 우대는 상품 옆에 네 종류 메모 중 하나로 남는다
- 실제 모델이 칸을 크게 지어내지 않는다 (모르면 `UNRESOLVED`)
- 한 턴 대기 시간이 쓰기 요청에서 감당할 만하다

### 아직 성공이 아닌 것

- 가짜 상품에서 금리가 2에서 3으로 오른 것
- 전체 pytest가 통과한 것 자체 (필요 조건이지 충분 조건이 아님)
